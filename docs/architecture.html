Authentication & Authorization Flow Keycloak + SPI

Login uses PKCE Authorization Code flow. The custom SPI bridges Keycloak to the user-service database — no user sync needed. Every authenticated API call is validated by KrakenD against Keycloak's JWKS, and claims are forwarded as HTTP headers.

1
Angular Frontend
Redirects user to Keycloak with PKCE code_challenge (client: mediq-frontend-spa, scopes: openid profile email roles)
2
Keycloak
Receives credentials → delegates to mediq-user-storage SPI → SPI queries mediq_users.users + user_contact, BCrypt-verifies password
3
Keycloak SPI
On success: reads role_permissions table, attaches role (DOCTOR/PATIENT/ADMIN/NURSE), userId, userType, permissions as user attributes
4
Keycloak
Issues RS256-signed JWT containing: sub, userId, email, role, userType, permissions, jti, exp — via realm-roles-mapper + attribute mappers
5
Angular Frontend
Stores token, attaches as Authorization: Bearer <token> on every API call to KrakenD
6
KrakenD
Fetches Keycloak JWKS from http://keycloak:8090/realms/mediq/protocol/openid-connect/certs, validates RS256 signature, checks issuer + expiry (cached 15 min)
7
KrakenD
On valid token: propagates claims as headers → X-User-Id, X-User-Email, X-User-Role, X-User-Type, X-User-Permissions, X-Token-Jti
8
Microservice
Reads X-User-Permissions header, enforces fine-grained access control (e.g. READ_EMR, WRITE_APPOINTMENT_SLOT) — no Spring Security, no DB call needed

Appointment Booking Workflow Temporal orchestration

Appointment booking is a multi-step saga orchestrated by Temporal. The workflow guarantees atomicity across payment and notification — if payment fails, the appointment is never confirmed. A scheduler auto-cancels stale PENDING_PAYMENT appointments after 24 hours.

1
Frontend
POST /api/v1/appointments with doctorId, slotId, patientId (JWT required)
2
appointment-service
SELECT FOR UPDATE on slot → verify AVAILABLE → write appointment record (PENDING_PAYMENT) + outbox entry atomically
3
Temporal Workflow
appointment-service starts AppointmentBookingWorkflow on appointment-booking-queue with appointmentId as workflow ID
4
PaymentActivity
HTTP POST to payment-service:8089/payments/intent — Stripe creates PaymentIntent, returns clientSecret to frontend
5
Frontend
Stripe.js confirms payment with clientSecret → Stripe webhook fires to payment-service
6
payment-service
Webhook handler verifies Stripe signature → records PAYMENT_SUCCEEDED → signals Temporal workflow → publishes mediq.payment.events
7
Temporal Workflow
Receives payment signal → executes NotificationActivity → HTTP POST to notification-service:8085/notifications/send
8
appointment-service
Updates appointment → CONFIRMED → writes outbox → Debezium publishes mediq.appointment.events (AppointmentConfirmed)
9
notification-service
Consumes AppointmentConfirmed + PAYMENT_SUCCEEDED → sends confirmation email via Mailtrap SMTP
⏱
Timeout Path
PaymentTimeoutScheduler (runs every 1 min) finds appointments PENDING_PAYMENT > 24h → cancels → publishes AppointmentAutoCalculated → notification-service sends timeout notice

Observability Stack traces · metrics · logs

All services instrument via Micrometer + OpenTelemetry. Traces flow to Jaeger; metrics scraped by Prometheus and dashboarded in Grafana; logs shipped by Promtail to Loki.
